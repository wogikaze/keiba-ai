# 特徴量を「いつ確定するか」で線引きし、リークと group の誤りを合成データで測った LGBMRanker の実装ガイド

> 一言で: 競馬の定番特徴量を6カテゴリに整理し、JRA の公表時刻（出馬表・枠順・馬体重・オッズ）から「予想する時刻に使える列」を決める手順と、LightGBM 4.7.0 の LGBMRanker の実装をまとめた企業技術ブログ。数値はすべて合成データ（6,000レース）で、全期間で集計した馬の成績を入れるとテストで勝率 43.7% に見えるが、運用条件では 39.7% と正しく作ったモデル（40.1%）を下回る、というリークの大きさを示している。実データの回収率は出していない。

ソフトウェア受託会社のテックブログ。HTML のメタデータでは初出 2024年5月29日、最終更新 2026年10月13日で、取得した版は LightGBM 4.7.0・pandas 3.0.6・scikit-learn 1.9.1 と 2026年9月の JRA 発表に言及している。ノートは 2026 年版の内容に基づく。著者個人の名前は出ていない。

## データ

- 実データは使っていない。特徴量の数値比較は合成データ: 1回あたり 6,000 レース・約 7.2 万行（馬 3,000 頭・騎手 120 人）。着順は「馬の能力・騎手の腕・偶然」で決まり、スピード指数にはクラス差が乗るよう生成（「競馬特有の特徴量エンジニアリング」の節）。
- 分割は時系列: 古い 4,200 レースで学習、続く 600 レースを早期終了用の検証、最後の 1,200 レースをテスト。乱数種 0・1・2 の3通りの平均。
- 実データの入手先としては JRA-VAN DataLab.（月額 2,090 円、1986 年から）とスクレイピング（利用規約・robots.txt の確認）を挙げる（FAQ）。

## 特徴量（カタログ）

6カテゴリの表で、型と作り方を付けて一覧にしている。

- 馬の基本情報・血統: 馬番・枠番、性、馬齢、斤量、馬体重・増減、父・母父、種牡馬別の芝ダ・距離別産駒成績、生産者・馬主。
- 過去成績・スピード指数: 前走着順・着差、過去 N 走の平均着順・複勝率、距離・コース・馬場別成績、スピード指数、上がり3F、通過順・脚質、レース間隔、距離延長・短縮。
- レース条件・展開: 距離、芝ダ、回り、馬場状態（順序カテゴリ）、天候、頭数、クラス（順序カテゴリ）、開催場、「逃げ・先行馬の頭数」を想定ペースの代理に。
- 騎手・調教師: 勝率・複勝率、騎手×コース・距離成績（騎乗数を添える）、乗り替わり、調教師勝率・所属。
- 調教・馬具: 最終追い切りタイム（レース内相対化）、追い切り本数、馬具変更フラグを先に入れ、パドック評価は評価者で意味が変わるので後回し。JRA-VAN が 2021年10月からウッドチップ調教データを提供していることにも触れている。
- オッズ・人気: 予想する時刻のオッズを使い、確定オッズは入れない。前日から締切前までのオッズの変動も候補。

## 情報の確定時刻とリークの線引き

「特徴量ごとの確定タイミング」の節で、JRA の公表時刻を表にしている（JRA 番組・FAQ・馬体重ページを出典として明記）。

| 情報 | 公表時点（JRA通常開催） |
|---|---|
| 出馬投票締切 | 原則木曜 14:30（新規）/ 14:45（変更・取消） |
| 出馬表（馬番なし） | 木曜 16 時すぎ |
| 出馬表（枠番・馬番付き） | 前日 10 時すぎ |
| 馬体重 | 発走の概ね 65 分前に計量（2026年9月公表。同年1月は「概ね60分前」） |
| 単勝オッズ | 発売締切まで変動 |

結論として、前日夜に予想を確定させる運用なら馬体重は特徴量から外す。学習データには全レースの馬体重があるので、入れたまま検証すると運用で手に入らない列で精度を測ることになる。JRA サイトへの表示は発表後約 15 分かかる場合があるので、取得経路で実際に使えた時刻を記録する、とも書く。

## モデルと目的変数

- LGBMRanker（objective=lambdarank、metric=NDCG@3）。group は各レースの頭数。
- ラベル（relevance）: 1着=3、2〜3着=2、4〜5着=1、それ以外=0。既定の label_gain は 2^label − 1 なので、1着（利得7）は2〜3着（利得3）の2倍以上重い。ラベルの上限は既定で 30 で、31 以上を入れると `LightGBMError: Label 33 is not less than the number of label mappings (31)` で止まる。
- 取消・除外・中止・失格など着順が正の整数でない行は例外で止め、扱いを先に決めさせる。
- 特徴量は除外リストではなく許可リストで指定する（後から上がりや払戻の列が増えても混入しない）。
- 分類（LGBMClassifier）との使い分け: ランキングの出力は確率ではないので、オッズと掛けて期待値で買うなら分類モデルを併用する。

## 結果（合成データ）

レース内相対化（「特徴量のレース内相対化」の節。ランダムに1頭選んだときの勝率 8.7%）:

| 特徴量 | NDCG@3 | 予測1位の勝率 |
|---|---|---|
| 生のスピード指数のみ | 0.5331 | 28.3% |
| 相対化したスピード指数のみ | 0.5376 | 28.2% |
| 生のスピード指数＋騎手勝率 | 0.5723 | 32.1% |
| 相対化＋騎手勝率 | 0.5777 | 32.3% |

過去走集約のリーク（「過去走の集約とターゲットエンコーディングのリーク防止」の節）:

| 馬の成績の作り方 | 評価条件 | NDCG@3 | 予測1位の勝率 |
|---|---|---|---|
| 過去走だけ | テスト | 0.6482 | 40.1% |
| 全期間（リーク） | テスト（リーク列のまま） | 0.6830 | 43.7% |
| 全期間（リーク） | 本番と同じ条件 | 0.6468 | 39.7% |

騎手勝率を全期間で作った場合は 31.9%（過去だけは 32.3%）で差が出なかった。騎手1人あたり約 600 騎乗あり、1レースの結果が平均をほとんど動かさないため、と説明している。出走数の少ないカテゴリ（馬）の集約から点検すべき、が結論。

group の誤り（「レース単位・時系列での分割」の節）: 学習側の行をシャッフルして group をずらしても LightGBM はエラーを出さない。生の値では予測1位の勝率が 32.1% → 29.3% に下がり、相対化した列では 32.3% → 32.2% でほぼ変わらない。精度が落ちないこともあるので、指標では誤りに気付けない。同じレースの行が連続しているかを assert で確かめるコードを載せている。

## 評価（回収率の扱い）

- 回収率は、学習にも早期終了にも使っていないテスト期間で、モデルと買い方を固定して測る。
- 精算は特徴量のオッズではなく、公式払戻金の列（100円あたり、不的中0円、返還100円）で行う。予想時刻のオッズは確定オッズと違うので、同じ列で精算すると払戻と一致しない。
- 比較基準は「予想時刻の単勝オッズが最も低い馬を買い続けた場合」。
- JRA の設定払戻率（単複 80%、枠連・馬連・ワイド 77.5%、馬単・3連複 75%、3連単 72.5%、WIN5 70%）を表で示し、最初の検証は単勝・複勝で行うべきとする。設定払戻率は個々の購入者の長期回収率を保証する値ではない、という注意も付けている。
- `GridSearchCV(scoring='ndcg')` は scikit-learn 1.9.1 にスコアラーがなく書けない。探索は group と時系列を保った分割を自前で組む。

## 落とし穴と教訓

- 全期間集計の成績特徴は、テストで良く見えて本番で負ける。「3.6ポイントの上積みは幻」。
- 行のシャッフル後に group を作ると、黙って間違った学習をする。
- LightGBM 4.x の API 変更: `early_stopping_rounds` は 4.0.0 で削除され callbacks で指定する。4.7.0 では `eval_set` が非推奨で `eval_X`・`eval_y`。pandas 3.0 の str 型カテゴリはそのままだと ValueError で、`astype('category')` が必要。

## 批判的に読む

- 数値はすべて作者が設計した合成データによる。生成過程に能力・騎手・偶然しかないので、相対化の効果が小さい、騎手集計のリークが小さい、といった結論が実データでも成り立つかは分からない。実データでは騎手の勝率は時期で動き、馬の成績は出走数が少ないので、リークの大きさはむしろ馬側で実データの方が大きい可能性がある。
- 実データの回収率がなく、「1番人気買いを上回るか」の答えは出していない。
- 記事の末尾に自社の受託開発サービスへの導線がある。内容は実装の注意として妥当だが、検証された予測手法の報告ではない。
- 公表時刻は JRA 通常開催の話で、G1 など前日発売のレースや地方競馬では異なる（記事でも前日発売の注記に触れている）。

## keiba-ai での使い方

- 情報の確定時刻の表は、keiba-ai の特徴量の「予測時点」を決める ADR の下書きに使える。特に馬体重（発走約65分前、サイト表示はさらに最大15分遅れ）は、前日予測か当日予測かで採否が変わる列として明示する。
- 特徴量を許可リストで管理し、`config.yaml` に列名を列挙する。上がり・払戻・着順の列が学習に入らないことをテストで確かめる。
- group 作成前に「同じ race_id の行が連続していること」を assert する。記事のコードはそのまま `src/keiba_ai/` に移せる。
- 馬・騎手の集計特徴は「そのレースより前だけ」の cumsum 方式で作り、全期間版との比較を一度だけ実験として残すと、リークの大きさを実データで測れる（記事の合成データの結果と比べる）。
- 回収率の精算は払戻テーブルを別に結合し、特徴量のオッズ列と分ける。ベースラインは購入時刻の1番人気。
